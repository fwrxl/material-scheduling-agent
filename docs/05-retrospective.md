# 05 复盘与改进

## 最难的问题

最难的不是把工具依次调通，而是同时保证“模型可以动态决策”和“关键业务状态不能由模型编造”。如果完全由固定代码决定流程，就不满足 ReAct；如果完全信任模型最终 JSON，又可能把保存失败说成成功，或把替代时段说成已确认。

项目采用的折中是：模型负责逐轮选择动作、参数和结束时机，业务层负责前置条件、时段可用性、幂等与真实写入，最后由确定性归约器计算任务状态。这样既保留真实模型的观察后调整空间，也守住确认和保存边界。

另一个实际问题是幂等比较。草稿记录比保存请求多出 `draft_id` 和 `created_at`，直接比较整条记录会误判重复请求。实现改为只比较业务负载字段，并通过连续两次完整 Agent 执行验证只有一份草稿。

完整交付后又进行了独立对抗审查，发现后续失败保存可能覆盖先前成功事实、其他素材审核可能污染当前结果，以及异常模型响应和损坏存储记录的校验缺口。修复增加了场景状态隔离、成功保存事实保留、严格响应/记录/参数校验，并用 20 项新增对抗测试验证。这个过程说明“正常路径通过”不等于异常路径的状态仍然可信。

## 技术收获

- ReAct 的可验证核心是模型响应工具观察后改变下一动作，而不是日志里出现“思考”或固定重试。
- 工具结果和最终用户结果应该分离；关键状态最好由可测试的业务事实生成。
- 确认边界需要数据模型支持。分别保存 `requested_start`、`suggested_start` 和 `confirmation_status`，比在自然语言中提醒更可靠。
- 幂等既要识别相同请求，也要拒绝同键不同内容；保存失败不能留下貌似成功的输出。
- Mock 很有价值，但只能证明流程。明确标记其边界比制造一份看似完整的真实模型记录更重要。

## 当前未完成部分

- 未使用真实模型 API 做在线端到端验证，需候选人提供合法凭据后执行。
- 未实现多素材、跨日排期、用户确认后的第二轮交互和真实发布；这些不在本次核心范围内。
- 未实现生产级多进程锁、数据库事务和断点续跑。
- 候选人的个人修改、独立验证和实际工时需要在提交前如实补充。

## 下一步

1. 用至少两种支持 tool calling 的真实模型运行正常、冲突、风险和保存失败场景，统计非法参数率、错误保存尝试率与任务成功率。
2. 增加用户确认/拒绝替代时段的输入路径，并验证原硬性要求只有在明确确认后才更新。
3. 将草稿存储替换为带唯一约束和事务的数据库，增加并发重复提交测试。
4. 将任务状态持久化，支持从最后成功观察恢复，而不是重复有副作用的步骤。
5. 扩展规则适用范围、时区和多素材资源冲突，并保持引用规则与输出原因可追踪。
