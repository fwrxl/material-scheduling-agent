# 01 需求说明

## 用户与问题

内容团队需要从待处理素材中识别可排期项，在审核规则和已有排期约束下形成可确认的发布草稿。用户关心四件事：素材能否进入排期、风险原因是什么、建议何时发布、草稿是否确实保存。

## 目标

输入素材 ID、期望发布时间和请求 ID，Agent 通过素材读取、规则检查和时段查询形成排期结果。若原时段冲突，可以建议替代时段，但不能替用户同意变更；系统只保存草稿，不接入真实发布。

## 输入与合成资料

- 场景输入：`scenario_id`、`request_id`、`material_id`、`requested_start`、硬性时间标记、执行上限和可选故障注入。
- `data/materials.json`：6 个合成素材，包含正常、缺负责人和命中功效宣传规则的数据。
- `data/rules.json`：必填字段和阻断规则 R01。
- `data/schedule.json`：2027-04-10 的 18:00 已占用，19:00 和 20:00 可用。

所有内容均为合成资料，不包含真实企业或个人信息。

## 交付结果

每个场景输出：

- `review_status`：通过、信息不完整、阻断或未检查；
- `risk_reasons`：缺失字段或命中规则；
- `requested_start` 与 `suggested_start`：区分硬性要求和建议；
- `pending_confirmations`：替代时段需要用户确认的事项；
- `draft.save_status`：已保存、重复、失败或未尝试；
- `task_status`：完成、等待确认、阻断、失败或未完成；
- `publication_status`：只表示草稿状态，不存在“已发布”。

Trace 另记录每步动作、工具参数、观察摘要、后续动作和简短决策依据，不包含隐藏思维过程。

## 范围

### 包含

- 单素材 CLI 处理；
- 原生模型工具调用循环和离线 Mock 入口；
- 草稿本地 JSON 原子写入、幂等和故障返回；
- 步数/工具次数上限；
- 自动化测试与实际运行材料。

### 不包含

- 真实发布、用户通知、网页界面和线上部署；
- 多素材批量业务优化、多 Agent、生产级持久化与分布式锁；
- 跨进程任务恢复和失败续跑；
- 未经真实 API 验证的模型效果声明。

## 成功标准与验收映射

| 验收点 | 成功标准 | 场景 |
|---|---|---|
| 正常排期 | 审核通过，保持可用原时段，实际保存一份草稿 | `normal` |
| 素材信息缺失 | 列出缺失字段，不查询排期、不保存 | `missing_info` |
| 规则风险 | 返回规则 ID 与原因，阻断保存 | `rule_risk` |
| 时段冲突 | 保留 18:00 原要求，建议 19:00，标记待确认 | `slot_conflict` |
| 重复提交 | 相同请求返回原草稿 ID，存储仅一份 | `duplicate` 连续运行两次 |
| 保存失败 | 返回失败、无草稿 ID、无成功文件 | `save_failure` |
| 动态路径 | 工具观察不同导致后续动作/参数与结束状态不同 | 正常与冲突 Trace 对照 |
| 执行上限 | 明确返回未完成及终止原因 | `step_limit` 与 `tool_call_limit` 均有运行记录 |
| 流程验证材料 | 输入、实际输出、Trace 和测试报告可复查 | `examples/` |

## 关键边界

1. “建议 19:00”不等于用户同意 19:00，更不等于已经发布。
2. 模型结束语不能覆盖工具失败；最终状态根据观察归约。
3. Mock 只验证流程，不证明真实模型决策效果。
4. 同一 `request_id` 若携带不同内容，返回幂等冲突而不是覆盖旧草稿。
